# ExamMate 关键设计决策（迁移参考）

> 来源：`decisions.md`
> 清洗说明：仅保留设计层面的决策，移除文档管理、测试策略、RAG 集成等实现层面的决策

---

## D001：注册式扩展 vs 继承框架

**决策**：采用注册式扩展架构，不继承框架类。

**理由**：
1. 框架的 Registry 机制就是为注册式扩展设计的标准方式
2. 职责边界最清晰——框架管 Agent 运行和记忆，业务管冲刺逻辑
3. 最小代码量——不需重写框架，不需子类，只需注册业务组件
4. 与产品定位一致——ExamMate 是运行在已有平台上的智能体

**替代方案**：创建框架 Application 子类（rejected：职责混杂，代码量大）

**迁移启示**：DeepTutor 的 Capability 机制天然支持这种模式——新能力只需实现 BaseCapability 接口并注册即可。

## D002：Vector-based vs File-based 记忆系统

**决策**：使用 vector-based 记忆系统。

**理由**：
1. 提供 CRUD API，UI 前端可直接通过 HTTP/MCP 调用读写状态
2. 语义检索能力——学生说"我想看看传输层薄弱点"，可语义匹配
3. Profile 演进能力——AbilityProfile 随时间变化
4. 对学生用户更友好——file-based 只能操作文件，没有结构化接口

**替代方案**：file-based 记忆（rejected：无语义检索，无结构化接口）

**迁移启示**：DeepTutor 的三层记忆（L1/L2/L3）可承接此需求，L2 层适合存储这类演进型业务状态。

## D003：CLI 优先 vs HTTP 优先

**决策**：V0 先以 CLI 模式验证，验证可行后切换 HTTP 模式。

**理由**：
1. CLI 模式迭代最快——终端对话式 Agent，每一步输入输出可直接观察
2. 不依赖前端开发
3. HTTP 模式只需切换 service backend，Agent Core 不变

**迁移启示**：DeepTutor 已有 CLI、WebSocket API、Python SDK 三种入口，天然支持多模式部署。

---

## D004：三阶段冲刺机制

**决策**：阶段规划期(≥14天) → 高压冲刺期(4-13天) → 临考保分期(≤3天)。

**理由**：
1. 不同时间窗口使用不同冲刺策略，避免前期碎片化、后期计划崩盘
2. 粒度切换机制让用户知道该保什么、放什么
3. 与产品核心创新点一致——时间压力驱动的规划粒度切换

**迁移启示**：这是 ExamMate 的核心创新，迁移时应完整保留此机制。

---

## D005：Pydantic v2 作为数据模型

**决策**：使用 Pydantic v2 定义所有业务数据模型。

**理由**：
1. 类型安全——运行时验证
2. 序列化/反序列化方便（JSON/YAML）
3. IDE 支持好（自动补全、类型检查）

**迁移启示**：DeepTutor 已广泛使用 Pydantic，数据模型可直接复用。
