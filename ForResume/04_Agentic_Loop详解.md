# Agentic Loop 详解 — 面试解读

> 本文档从面试角度解读 DeepTutor 的 Agentic Loop（代理循环）实现，帮助你在面试中清晰表达技术细节。

---

## 一、模块总览

### 1.1 这个模块解决什么问题？

Agentic Loop 是 DeepTutor 的**核心推理引擎**，解决的核心问题是：

**如何让 LLM 能够自主调用工具、处理中间结果、并最终完成复杂任务？**

传统 LLM 调用是一次性的（输入→输出），但真实场景中 LLM 需要：
- 调用外部工具（RAG 检索、代码执行、网络搜索）
- 处理工具返回的结果
- 根据结果决定下一步行动
- 在多轮迭代后给出最终答案

Agentic Loop 就是实现这个**"思考→行动→观察→再思考"**循环的引擎。

### 1.2 核心设计理念

采用**标签驱动**的设计，核心思想是：

> LLM 的每次输出都带有一个**协议标签**，系统根据标签类型决定下一步做什么。

这种设计的好处是：
- **结构化**：LLM 输出有明确的语义，不会出现模糊状态
- **可预测**：系统行为完全由标签决定，易于理解和调试
- **可扩展**：新增能力只需定义新的标签协议

## 二、内部分层架构

### 2.1 组件组成

Agentic Loop 由**四层组件**组成：

```
┌─────────────────────────────────────────────────────────────┐
│                    应用层 (Application Layer)                 │
│                                                             │
│   Chat Pipeline    Solve Pipeline    Research Pipeline      │
│   (对话能力)        (解题能力)         (研究能力)             │
│                                                             │
├─────────────────────────────────────────────────────────────┤
│                    协议层 (Protocol Layer)                    │
│                                                             │
│   LabelProtocol    LoopOutcome       LoopHost               │
│   (标签协议)        (循环结果)         (宿主接口)             │
│                                                             │
├─────────────────────────────────────────────────────────────┤
│                    调度层 (Scheduling Layer)                  │
│                                                             │
│   run_agentic_loop    labeled_step    tool_dispatch          │
│   (循环调度器)         (步骤执行器)     (工具分发器)           │
│                                                             │
├─────────────────────────────────────────────────────────────┤
│                    基础层 (Infrastructure Layer)              │
│                                                             │
│   LLM Client    Tool Registry    Memory Store    Stream Bus  │
│   (LLM客户端)    (工具注册中心)     (记忆存储)      (流总线)   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 各层职责

| 层级 | 职责 | 核心组件 |
|------|------|---------|
| **应用层** | 定义具体能力的业务逻辑 | Chat/Solve/Question/Research Pipeline |
| **协议层** | 定义标签词汇表和循环结果 | LabelProtocol, LoopOutcome, LoopHost |
| **调度层** | 执行循环、调用 LLM、分发工具 | run_agentic_loop, labeled_step, tool_dispatch |
| **基础层** | 提供 LLM、工具、记忆等基础设施 | LLM Client, Tool Registry, Memory Store |

### 2.3 组件关系图

```
应用层 Pipeline
      │
      ▼
┌─────────────────┐
│  LoopHost 实现   │ ◄─── 每个 Pipeline 实现自己的 LoopHost
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ run_agentic_loop│ ◄─── 调度层核心，接收 LoopHost + LabelProtocol
└────────┬────────┘
         │
         ▼
┌─────────────────┐     ┌─────────────────┐
│  labeled_step   │────►│  LLM Client     │
│  (步骤执行器)    │     │  (调用LLM)      │
└────────┬────────┘     └─────────────────┘
         │
         ▼
┌─────────────────┐     ┌─────────────────┐
│  tool_dispatch  │────►│  Tool Registry  │
│  (工具分发器)    │     │  (执行工具)      │
└─────────────────┘     └─────────────────┘
```

## 三、核心数据流

### 3.1 完整循环流程

一次完整的 Agentic Loop 执行包含以下阶段：

```
用户输入
    │
    ▼
┌───────────────────────────────────────────────────────────────┐
│  阶段 1：初始化                                                │
│  - 应用层 Pipeline 创建 LoopHost 实现                          │
│  - 配置 LabelProtocol（定义允许的标签）                         │
│  - 初始化消息列表（包含系统提示词 + 用户输入）                    │
└───────────────────────────────────────────────────────────────┘
    │
    ▼
┌───────────────────────────────────────────────────────────────┐
│  阶段 2：LLM 调用                                              │
│  - labeled_step 将消息列表 + 工具 schema 发送给 LLM             │
│  - LLM 返回带标签的输出（如 [THINK] 分析问题...）               │
│  - 解析输出，提取标签和内容                                      │
└───────────────────────────────────────────────────────────────┘
    │
    ▼
┌───────────────────────────────────────────────────────────────┐
│  阶段 3：协议验证                                              │
│  - 检查标签是否在 LabelProtocol.allowed 列表中                  │
│  - 如果不在 → 协议违规，发送修复消息，回到阶段 2                 │
│  - 如果在 → 进入阶段 4                                         │
└───────────────────────────────────────────────────────────────┘
    │
    ▼
┌───────────────────────────────────────────────────────────────┐
│  阶段 4：标签分发                                              │
│  根据标签类型执行不同逻辑：                                      │
│                                                               │
│  ┌─────────────────┐                                          │
│  │ 终止标签        │ → 退出循环，返回 LoopOutcome              │
│  │ (FINISH/REPLAN) │                                          │
│  └─────────────────┘                                          │
│                                                               │
│  ┌─────────────────┐                                          │
│  │ 工具标签        │ → 解析工具调用，并行执行，收集结果          │
│  │ (TOOL)          │ → 将结果添加到消息列表，回到阶段 2          │
│  └─────────────────┘                                          │
│                                                               │
│  ┌─────────────────┐                                          │
│  │ 中间标签        │ → 保留上下文，回到阶段 2                   │
│  │ (THINK)         │                                          │
│  └─────────────────┘                                          │
└───────────────────────────────────────────────────────────────┘
    │
    ▼
┌───────────────────────────────────────────────────────────────┐
│  阶段 5：返回结果                                              │
│  - LoopOutcome 包含：final_label, final_text, iterations      │
│  - 应用层 Pipeline 处理结果，返回给用户                         │
└───────────────────────────────────────────────────────────────┘
```

### 3.2 工具调用子流程

当标签是 `TOOL` 时，进入工具调用子流程：

```
LLM 输出 [TOOL] + 工具调用列表
    │
    ▼
┌───────────────────────────────────────────────────────────────┐
│  步骤 1：解析工具调用                                          │
│  - 从 LLM 输出中提取工具名称和参数                              │
│  - 可能包含多个工具调用（如同时调用 RAG + web_search）           │
└───────────────────────────────────────────────────────────────┘
    │
    ▼
┌───────────────────────────────────────────────────────────────┐
│  步骤 2：并行执行                                              │
│  - 使用 asyncio.gather 并行执行所有工具调用                     │
│  - 每个工具独立执行，互不干扰                                   │
│  - 单个工具失败不影响其他工具                                   │
└───────────────────────────────────────────────────────────────┘
    │
    ▼
┌───────────────────────────────────────────────────────────────┐
│  步骤 3：收集结果                                              │
│  - 按调用顺序收集执行结果                                       │
│  - 失败的工具返回错误信息                                       │
│  - 成功的工具返回执行结果                                       │
└───────────────────────────────────────────────────────────────┘
    │
    ▼
┌───────────────────────────────────────────────────────────────┐
│  步骤 4：更新上下文                                            │
│  - 将工具结果添加到消息列表                                     │
│  - 回到阶段 2，继续下一轮循环                                   │
└───────────────────────────────────────────────────────────────┘
```

#### 关键理解点

1. **LabelProtocol** 是配置，不是运行时组件
   - 循环开始前由应用层创建
   - 验证时只读（输入标签，输出是否合法）

2. **LoopHost** 是接口，由应用层实现
   - 调度器通过它获取工具列表
   - 调度器通过它执行工具（可自定义逻辑）

3. **labeled_step** 和 **tool_dispatch** 是调度器的"左右手"
   - labeled_step：调用 LLM，解析输出
   - tool_dispatch：执行工具，收集结果

4. **LoopOutcome** 是输出，循环结束时创建
   - 包含最终标签、最终文本、迭代次数
   - 返回给应用层处理

### 4.1 LabelProtocol（标签协议）

**职责**：定义 LLM 可以输出的标签词汇表。

**组成元素**：
- **allowed**：允许的标签列表（元组）
- **terminal**：终止标签（集合），遇到这些标签时退出循环
- **intermediate**：中间标签（集合），遇到这些标签时继续循环
- **final**：最终标签（集合），输出内容的标签
- **tool_label**：工具标签（字符串），遇到这个标签时执行工具调用

**设计特点**：
- 声明式定义：每个能力声明自己需要哪些标签
- 不可变：使用 frozen dataclass，运行时不可修改
- 可组合：不同能力可以复用相同的标签

**示例**：
- Solve Pipeline 的协议：允许 THINK/TOOL/FINISH/REPLAN
- Plan Pipeline 的协议：只允许 PLAN（单轮）

### 4.2 LoopOutcome（循环结果）

**职责**：封装一次循环的执行结果。

**包含信息**：
- **final_label**：最终标签（如 FINISH）
- **final_text**：最终输出文本
- **iterations**：迭代次数

**使用场景**：
- 应用层 Pipeline 获取循环结果
- 用于日志记录和性能统计
- 用于判断是否需要重试

### 4.3 LoopHost（宿主接口）

**职责**：定义应用层 Pipeline 需要实现的钩子。

**核心方法**：
- **get_tool_schemas()**：返回可用工具的 schema 列表
- **dispatch_tools()**：执行工具调用（可自定义逻辑）

**设计思想**：
- 循环核心不依赖具体能力
- 应用层通过 LoopHost 接入循环
- 每个 Pipeline 实现自己的 LoopHost

**示例**：
- Chat Pipeline 的 LoopHost：只暴露基础工具（RAG、memory）
- Solve Pipeline 的 LoopHost：暴露解题工具（code_execution、reason）

### 4.4 run_agentic_loop（循环调度器）

**职责**：执行 Agentic Loop 的核心逻辑。

**输入**：
- **host**：LoopHost 实现
- **messages**：消息列表（包含系统提示词 + 用户输入）
- **protocol**：LabelProtocol 实例
- **stream**：流式输出对象（可选）

**输出**：
- **LoopOutcome**：循环结果

**核心逻辑**：
1. 循环调用 labeled_step 获取 LLM 输出
2. 验证标签是否合法
3. 根据标签类型分发处理
4. 管理消息列表（添加助手输出、工具结果、修复消息）

**容错机制**：
- 协议违规时发送修复消息，重试当前迭代
- 限制最大迭代次数，避免无限循环
- 工具执行失败时返回错误信息，继续循环

### 4.5 labeled_step（步骤执行器）

**职责**：调用 LLM 并解析带标签的输出。

**输入**：
- **client**：LLM 客户端
- **messages**：消息列表
- **tool_schemas**：工具 schema 列表
- **protocol**：标签协议
- **stream**：流式输出对象

**输出**：
- **LabeledResult**：包含标签和内容

**处理逻辑**：
1. 将消息列表 + 工具 schema 发送给 LLM
2. 接收 LLM 输出
3. 解析输出，提取标签和内容
4. 返回 LabeledResult

**标签解析**：
- 使用正则表达式或字符串匹配提取标签
- 处理边界情况（多个标签、无标签、格式错误）

### 4.6 tool_schemas（工具清单）

**职责**：告诉 LLM 有哪些工具可用，以及如何调用。

**通俗理解**：tool_schemas 就是"餐厅菜单"：
- **你（LLM）** = 顾客
- **tool_schemas** = 菜单
- **Agent 系统** = 服务员

菜单告诉你：
1. 有哪些菜可以点（工具名称）
2. 每道菜需要什么配料（参数）
3. 哪些是必选的，哪些是可选的（required）

**具体例子**：

假设有一个 `search_knowledge` 工具：
```
name: search_knowledge        # 工具名称（菜名）
description: 搜索知识库        # 工具描述（菜品介绍）
parameters:                   # 参数列表（配料）
  query:                      # 参数名
    type: string              # 参数类型
    description: 搜索关键词    # 参数说明
    required: true            # 是否必选
  top_k:
    type: integer
    description: 返回结果数量
    required: false
```

**怎么起作用**？

1. **发送给 LLM**：系统把 tool_schemas 作为"菜单"发给 LLM
   ```
   你可以使用以下工具：
   1. search_knowledge(query: string, top_k?: integer)
      - query: 搜索关键词（必填）
      - top_k: 返回结果数量（可选，默认5）
   ```

2. **LLM 决定调用**：LLM 根据用户问题和"菜单"决定调用什么
   ```
   用户问："什么是傅里叶变换？"
   LLM 想：我需要搜索知识库，调用 search_knowledge
   ```

3. **系统验证和执行**：系统根据 schema 验证调用是否合法
   - 工具名称是否存在？ ✓
   - 参数类型是否正确？ ✓
   - 必填参数是否都有？ ✓

**为什么需要 tool_schemas**？

| 问题 | 没有 tool_schemas | 有 tool_schemas |
|------|------------------|-----------------|
| LLM 知道有什么工具吗？ | 不知道 | 知道 |
| LLM 知道怎么调用吗？ | 不知道 | 知道 |
| 系统能解析 LLM 输出吗？ | 不能 | 能 |
| 系统能验证调用合法吗？ | 不能 | 能 |

**在 Agentic Loop 中的位置**：
- 循环开始前：LoopHost.get_tool_schemas() → 获取工具列表
- 每轮迭代：labeled_step(messages, tool_schemas) → 发给 LLM
- LLM 根据 tool_schemas 决定是否调用工具
- 如果调用：解析 tool_calls，执行工具
- 如果不调用：直接返回结果

**关键理解**：tool_schemas 是 LLM 和工具之间的"契约"，让 LLM 能够正确地调用工具。

### 4.7 tool_dispatch（工具分发器）

**职责**：并行执行工具调用。

**输入**：
- **tool_calls**：工具调用列表（从 LLM 输出解析）
- **registry**：工具注册中心

**输出**：
- **DispatchOutcome**：包含工具消息列表

**处理逻辑**：
1. 解析每个工具调用（名称 + 参数）
2. 使用 asyncio.gather 并行执行
3. 收集执行结果（成功/失败）
4. 按调用顺序返回工具消息

**异常处理**：
- 单个工具失败不影响其他工具
- 失败的工具返回错误信息
- 记录日志便于排查

## 五、面试题与参考答案

### 面试题 1：请描述 Agentic Loop 的整体架构

**参考答案：**

Agentic Loop 采用**四层架构**设计：

1. **应用层**：定义具体能力的业务逻辑（如 Chat、Solve、Research）
2. **协议层**：定义标签词汇表和循环结果，是循环的"规则手册"
3. **调度层**：执行循环的核心逻辑，包括 LLM 调用、标签验证、工具分发
4. **基础层**：提供 LLM、工具、记忆等基础设施

**核心设计思想**是**标签驱动**：LLM 的每次输出都带有一个协议标签，系统根据标签类型决定下一步做什么。这种设计确保了 LLM 输出的结构化和可预测性。

**数据流**：用户输入 → 初始化消息列表 → 循环调用 LLM → 验证标签 → 根据标签类型分发 → 返回结果

---

### 面试题 2：标签协议是如何设计的？

**参考答案：**

标签协议定义了 LLM 输出的**结构化格式**，包含四个维度：

1. **允许的标签列表**：LLM 可以输出哪些标签（如 THINK、TOOL、FINISH）
2. **终止标签**：遇到这些标签时退出循环（如 FINISH、REPLAN）
3. **中间标签**：遇到这些标签时继续循环（如 THINK）
4. **工具标签**：遇到这个标签时执行工具调用（如 TOOL）

**设计特点**：
- **声明式**：每个能力声明自己需要哪些标签，而非硬编码
- **不可变**：使用 frozen dataclass，运行时不可修改，保证安全性
- **可组合**：不同能力可以复用相同的标签（如都使用 THINK）

**示例**：Solve Pipeline 定义了 THINK/TOOL/FINISH/REPLAN 四个标签，其中 FINISH/REPLAN 是终止标签，THINK 是中间标签，TOOL 是工具标签。

---

### 面试题 3：循环调度器是如何工作的？

**参考答案：**

循环调度器是 Agentic Loop 的核心，负责**驱动整个循环**：

**工作流程**：
1. **初始化**：接收 LoopHost、消息列表、标签协议
2. **循环调用 LLM**：使用 labeled_step 调用 LLM 获取带标签的输出
3. **验证协议**：检查标签是否在允许列表中
4. **分发处理**：根据标签类型执行不同逻辑：
   - 终止标签 → 退出循环，返回结果
   - 工具标签 → 执行工具调用，将结果添加到消息列表，继续循环
   - 中间标签 → 保留上下文，继续循环
5. **容错处理**：协议违规时发送修复消息，重试当前迭代

**关键设计**：
- **标签驱动**：根据标签类型决定行为，而非硬编码逻辑
- **上下文管理**：自动维护消息列表，包含助手输出、工具结果、修复消息
- **迭代控制**：限制最大迭代次数，避免无限循环

---

### 面试题 4：工具调用是如何并行执行的？

**参考答案：**

工具调用采用**并行分发**策略，核心思想是：

> 多个工具调用可以同时执行，互不干扰，最后按顺序收集结果。

**执行流程**：
1. **解析工具调用**：从 LLM 输出中提取工具名称和参数（可能有多个）
2. **并行执行**：使用 asyncio.gather 同时执行所有工具调用
3. **收集结果**：按调用顺序收集执行结果（成功/失败）
4. **更新上下文**：将结果添加到消息列表，继续循环

**关键设计**：
- **并行而非串行**：减少整体延迟（如同时调用 RAG + web_search）
- **异常隔离**：单个工具失败不影响其他工具，失败的工具返回错误信息
- **有序收集**：保证结果顺序与调用顺序一致，便于 LLM 理解

---

### 面试题 5：如何处理协议违规？

**参考答案：**

协议违规处理采用**自动修复**策略，核心思想是：

> LLM 输出了非法标签时，告诉它正确的格式，让它重试。

**违规场景**：
- LLM 输出了不在 allowed 列表中的标签
- LLM 输出了多个标签
- LLM 在工具标签后没有输出工具调用

**修复流程**：
1. **检测违规**：检查标签是否在 allowed 列表中
2. **发送修复消息**：告诉 LLM 正确的标签格式
3. **重试当前迭代**：不增加迭代次数，直接重试
4. **日志记录**：记录违规日志便于排查

**关键设计**：
- **自动修复**：无需人工干预，LLM 自我纠正
- **优雅降级**：违规时继续执行，不会崩溃
- **重试限制**：避免无限循环（有最大重试次数）

---

### 面试题 6：Agentic Loop 的优势是什么？

**参考答案：**

Agentic Loop 相比传统 LLM 调用有以下优势：

**结构化输出**：
- 传统方式：LLM 输出自由文本，需要正则提取，易出错
- Agentic Loop：LLM 输出带标签的结构化内容，易于解析

**工具集成**：
- 传统方式：手动分发工具调用，串行执行
- Agentic Loop：自动并行执行工具调用，减少延迟

**错误处理**：
- 传统方式：手动重试，容易遗漏
- Agentic Loop：协议违规时自动修复，工具失败时优雅降级

**上下文管理**：
- 传统方式：手动维护对话历史，容易出错
- Agentic Loop：自动管理消息列表，包含助手输出、工具结果、修复消息

**能力复用**：
- 传统方式：每个能力独立实现循环逻辑
- Agentic Loop：同一循环核心支持多种能力，只需实现 LoopHost 接口

## 六、技术亮点总结

### 6.1 架构设计亮点

1. **标签驱动**：LLM 输出有明确语义，系统行为可预测
2. **分层架构**：协议层、调度层、基础层职责清晰，易于维护
3. **能力无关**：循环核心不依赖具体能力，可复用性强

### 6.2 工程实现亮点

1. **并行工具调用**：减少整体延迟，提升用户体验
2. **自动修复机制**：协议违规时自动纠正，无需人工干预
3. **异常隔离**：单个工具失败不影响整体流程

### 6.3 面试加分点

1. **可扩展性**：新增能力只需实现 LoopHost + 定义 LabelProtocol
2. **可测试性**：协议定义清晰，易于单元测试
3. **可观测性**：迭代过程可追踪，便于调试和优化
