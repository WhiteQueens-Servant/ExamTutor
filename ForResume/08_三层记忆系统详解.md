# 08 三层记忆系统详解

> 面试考察点：Agent 长期记忆架构设计、LLM 驱动的信息整合、增量更新与容错机制

---

## 上半部分：讲解

### 1. 问题背景：Agent 为什么需要长期记忆？

一个 Agent-Native 学习系统有 7 种能力面（chat / notebook / quiz / kb / book / tutorbot / cowriter），每种能力面都会产生用户行为数据。如果每次对话都从零开始，Agent 就是一个"没有记忆的工具"，无法做到：

- **个性化**：记不住用户的学习进度、薄弱点、偏好
- **连续性**：跨 session 的学习上下文断裂
- **跨能力协同**：quiz 能力面发现的薄弱点，chat 能力面无法感知

传统方案是把所有历史塞进 context window，但这有硬上限——token 成本指数增长，且旧信息会"稀释"新信息。

**核心问题：如何在 token 有限的前提下，让 Agent 拥有跨能力、跨时间的长期记忆？**

### 2. 三层记忆架构总览

系统采用 L1 → L2 → L3 三层递进式记忆架构，每层职责清晰：

```
用户行为事件
  ↓ emit
┌─────────────────────────────────────────────────────────────────┐
│  L1：事件追踪层（Event Trace）                                    │
│  格式：append-only JSONL 文件                                     │
│  粒度：按功能面（surface）× 按日期（UTC day）                       │
│  内容：每次交互的原始事件（kind + payload + session/turn 信息）       │
│  定位：不可变的"原始日志"，永远不修改、不删除                         │
└─────────────────────────────────────────────────────────────────┘
  ↓ LLM 驱动整合（chunk-based update）
┌─────────────────────────────────────────────────────────────────┐
│  L2：功能面摘要层（Per-Surface Summary）                          │
│  格式：每个功能面一个 Markdown 文件                                 │
│  粒度：7 个文件（chat.md / notebook.md / quiz.md / ...）           │
│  内容：从 L1 事件中提取的事实性知识，按 section 组织                 │
│  定位：每个能力面的"独立记忆"，服务于该能力的上下文注入                │
└─────────────────────────────────────────────────────────────────┘
  ↓ LLM 驱动整合（chunk-based update）
┌─────────────────────────────────────────────────────────────────┐
│  L3：跨功能面全局记忆（Cross-Surface Global Memory）              │
│  格式：4 个槽位各一个 Markdown 文件                                │
│  粒度：recent / profile / scope / preferences                    │
│  内容：从 L2 摘要中提炼的全局知识                                   │
│  定位：所有能力共享的"用户全貌"，服务于 Agent 的全局上下文注入         │
└─────────────────────────────────────────────────────────────────┘
```

**数据流向**：L1（原始事件）→ L2（功能面摘要）→ L3（全局记忆）

每层向上一层提供输入，但不反向依赖——L2 整合时只读 L1，L3 整合时只读 L2，形成单向数据管道。

### 3. 存储布局与路径设计

整个记忆系统以"用户工作空间"为根目录，文件布局如下：

```
memory_root/
├── trace/                    # L1 事件追踪
│   ├── chat/
│   │   ├── 2025-07-01.jsonl
│   │   ├── 2025-07-02.jsonl
│   │   └── ...
│   ├── notebook/
│   ├── quiz/
│   ├── kb/
│   ├── book/
│   ├── tutorbot/
│   └── cowriter/
├── L2/                       # 功能面摘要
│   ├── chat.md
│   ├── notebook.md
│   ├── quiz.md
│   ├── kb.md
│   ├── book.md
│   ├── tutorbot.md
│   └── cowriter.md
├── L3/                       # 跨功能面全局记忆
│   ├── recent.md             # 近期动态
│   ├── profile.md            # 用户画像
│   ├── scope.md              # 学习范围
│   └── preferences.md        # 偏好（手动管理，不自动整合）
└── backup/                   # v1→v2 迁移归档
```

**设计要点**：

- **Surface（功能面）** 是记忆系统的核心分组维度，对应 Agent 的 7 种能力模式。每种能力面产生的事件天然隔离在自己的 trace 目录中。
- **L3 Slot（槽位）** 是跨能力面的全局维度。`recent` 记录近期动态，`profile` 记录用户画像，`scope` 记录学习范围，`preferences` 记录用户偏好。
- **`preferences` 特殊处理**：不参与自动整合（consolidation），只能通过用户显式操作修改。这是因为偏好信息的"正确性"高度主观，LLM 自动提炼可能偏离用户意图。
- 路径解析通过 `PathService` 延迟获取，支持多用户隔离——每个用户有独立的 `memory_root`。

### 4. L1 事件追踪层：不可变的原始日志

L1 是整个记忆系统的"地基"，设计原则是**永远不修改已有数据**。

**事件结构**（TraceEvent）：

| 字段 | 说明 |
|------|------|
| `id` | 全局唯一 ID，格式为 `surface:ULID`，天然按时间排序 |
| `ts` | UTC 时间戳，ISO 8601 格式 |
| `surface` | 所属功能面（chat / notebook / ... / cowriter） |
| `kind` | 事件类型（如 user_message、assistant_reply、tool_call 等） |
| `payload` | 事件载荷（自由格式 JSON） |
| `session_id` | 会话 ID（可选） |
| `turn_id` | 轮次 ID（可选） |

**写入机制**：

- 每个事件 append 到当天的 JSONL 文件（`trace/<surface>/<YYYY-MM-DD>.jsonl`）
- 写入使用 per-surface 的 asyncio Lock，避免同进程并发写入导致行交错
- append 失败只记日志不抛异常（"never breaks the producing surface"），确保记忆采集不干扰主流程
- 完全 append-only，没有 update/delete 操作

**读取机制**：

- `iter_since(surface, since)`：按时间顺序遍历事件，支持时间过滤
- `count_since(surface, since)`：统计自某时间点以来的事件数量
- `iter_by_ids(ids)`：根据 trace ID 反查原始事件，支持跨 surface 查询
- 读取是纯函数式的，从文件头到尾顺序扫描，利用文件名排序（日期 ISO 格式天然有序）做粗粒度时间过滤

**backlog 机制**：L2 的 `DocOverview` 中有一个 `backlog` 字段，表示"自上次 L2 整合以来，该 surface 产生了多少条新 L1 事件"。这为 Workbench UI 提供了直观的"待整合"提示——当 backlog > 0 时，用户知道 L2 摘要可能过期了。

### 5. L2/L3 写入：LLM 驱动的增量整合

L2 和 L3 的更新不是简单的"重新生成摘要"，而是一个精心设计的**增量整合管道**。

#### 5.1 增量去重机制

整合管道通过 meta 文件追踪"已处理的实体"：

- **L2 meta**：记录每个已处理的 L1 事件引用（`seen_entity_refs`，格式为 `surface:event_id`）
- **L3 meta**：记录每个已处理的 L2 条目引用（`seen_l2_entry_ids`，按 surface 分组）

每次整合时，先对比 meta 文件，只处理**新增的**实体，避免重复整合已有信息。这是增量更新的核心——不需要重新处理所有历史数据。

#### 5.2 Chunk-Based 处理

当新增实体数量较大时，文本会被切分为多个 chunk（带有 overlap 的滑动窗口），每个 chunk 独立调用 LLM 提取事实：

- chunk 大小由 `budget` 控制（L2/L3 有各自的默认预算）
- chunk 之间有 overlap，确保边界处的信息不丢失
- 每个 chunk 的处理结果独立追加到文档中
- 每次追加后做一次 checkpoint 写入，确保中间结果持久化

#### 5.3 引用链（Footnote Chain）

整合过程中的一个关键设计是**引用溯源**：

- L2 的每个条目都带有 `refs` 字段，引用原始 L1 事件的 trace ID
- L3 的每个条目引用 L2 的 surface 名称（而不是 L2 的条目 ID）
- 形成三层溯源链：**L3 → L2 md → L1 raw traces**

这为用户提供了完整的可追溯性——从一条全局记忆，可以一路追溯到产生它的原始对话事件。Workbench UI 支持点击 L3 的脚注跳转到对应的 L2 文件，再定位到具体的 L1 事件。

**为什么 L3 不直接引用 L1 的 entry ID？** 因为 L1 是按日期分文件的原始日志，entry ID 会随文件增长而变得难以管理。引用 surface 名称（文件级别）更简洁，且给用户一个清晰的 7-footnote 导航链。

#### 5.4 预览/应用两步流（Preview → Apply）

Workbench UI 支持"先预览、再应用"的两步操作：

1. **预览模式**（`apply_ops=False`）：运行完整的整合管道，但记录所有新增条目的 ID，然后**立即删除**这些新增条目。用户通过 SSE 事件流观察到整合过程和结果，但磁盘上不保留变更。
2. **应用模式**（`apply_ops=True`）：运行整合管道并保留结果。

预览模式的实现巧妙地复用了正式流程——不需要维护一套独立的"只读预览管道"。代价是预览时仍会写入磁盘再删除，不是真正的"零写入"，但保证了预览结果和实际应用的一致性。

#### 5.5 自动去重与合并

整合完成后，系统可自动触发两个后处理步骤：

- **Auto-Dedup**：LLM 驱动的去重，识别并合并语义重复的条目
- **Auto-Merge**：文档结构整理，合并碎片化的 section

这两个步骤通过配置开关控制（`settings.dedup.auto_after_update`、`settings.merge.auto_after_update`），可根据需要启用或禁用。

### 6. MemoryStore：统一的访问门面

所有对记忆层的读写操作都通过 `MemoryStore` 统一入口。它是一个无状态的门面（Stateless Facade），设计为进程级单例。

**核心能力**：

| 操作类别 | 方法 | 说明 |
|---------|------|------|
| L1 写入 | `emit(event)` | 追加事件到 trace |
| L2/L3 读取 | `read_doc(layer, key)` | 解析 Markdown 为 Document 对象 |
| L2/L3 读取 | `read_raw(layer, key)` | 读取原始 Markdown 文本 |
| L2/L3 读取 | `read_l3_concat()` | 拼接所有 L3 文档（供 read_memory 工具使用） |
| L2/L3 写入 | `overwrite_doc(layer, key, md)` | 用户手动保存（Workbench 编辑器） |
| L2/L3 写入 | `delete_entry(layer, key, entry_id)` | 删除单个条目 |
| L2/L3 整合 | `update_l2(surface)` / `update_l3(slot)` | 触发 LLM 驱动的增量整合 |
| L2/L3 写入 | `apply_ops_payload(layer, key, ops)` | 预览/应用两步流的"应用"阶段 |
| L3 偏好 | `write_preference(op, text, ...)` | 用户偏好写入（add/edit 两种操作） |
| 全局查询 | `overview()` | 返回所有 L2/L3 文档的元信息 + backlog |

**并发安全**：每个文件有独立的 asyncio Lock（`_write_locks` 字典，按文件路径索引），确保同一文件不会被并发写入。不同文件之间不互锁，最大化并发性。

**backlog 计算**：`overview()` 方法为每个 L2 文档计算 backlog——用 L2 文件的最后修改时间作为 cutoff，统计此后该 surface 产生的 L1 事件数量。这让 Workbench UI 能直观展示"chat 有 23 条未整合事件"之类的状态。

### 7. 设计原则与权衡

#### 7.1 为什么分三层而不是两层或一层？

- **一层**（只有 L1）：原始事件太多，token 成本不可接受
- **两层**（L1 + 全局摘要）：所有能力面的事件混在一起，摘要粒度太粗，无法为特定能力面提供精准上下文
- **三层**（L1 + L2 + L3）：L2 为每个能力面提供专属记忆，L3 提供跨能力的全局视角。粒度从细到粗，每层都有明确的消费者

#### 7.2 为什么 L1 要 append-only？

- **不可变性**保证了溯源的可靠性——原始数据永远不会被"整理"掉
- **append 操作**极其简单，不需要加文件锁（只需要 per-surface 的行写入锁）
- **崩溃安全**——即使进程崩溃，已 append 的行不会丢失（操作系统保证文件 append 的原子性）

#### 7.3 为什么整合是 LLM 驱动而不是规则驱动？

- L1 事件是自由格式的对话/行为数据，无法用正则或规则提取结构化知识
- LLM 能理解语义，可以从"用户在 quiz 中答错了 3 道线性代数题"提炼出"线性代数是薄弱点"
- 代价是每次整合需要调用 LLM API，但这是**离线批量操作**，不影响在线响应延迟

#### 7.4 为什么 preferences 不自动整合？

- 偏好的"正确性"高度主观——LLM 认为的偏好可能不是用户真正想要的
- 偏好的变更频率低，手动管理的负担可以接受
- 通过 `write_preference` 工具，Agent 可以在对话中"提议"偏好变更，但最终由用户确认

## 下半部分：面试 Q&A

### Q1：你的 Agent 系统的记忆是怎么设计的？

**答：** 采用三层递进式记忆架构。

L1 是事件追踪层，每个功能面每天一个 append-only JSONL 文件，记录所有原始交互事件。这层是不可变的"原始日志"，永远不修改。

L2 是功能面摘要层，每个功能面一个 Markdown 文件。通过 LLM 驱动的增量整合，从 L1 事件中提取事实性知识，按 section 组织。这层为每种能力模式提供专属记忆上下文。

L3 是跨功能面的全局记忆，分四个槽位——近期动态、用户画像、学习范围、偏好。从 L2 摘要中进一步提炼，所有能力共享。

数据流是单向的：L1 → L2 → L3，每层只依赖下一层，不反向依赖。

### Q2：为什么记忆要分三层，而不是两层？

**答：** 两层的问题是粒度不够。

如果只有 L1 + 全局摘要，所有能力面的事件混在一起做摘要，粒度太粗。比如 quiz 能力面发现的"线性代数薄弱"这个事实，会被 chat 能力面的大量闲聊对话稀释掉。

三层的好处是 L2 为每个能力面保留了专属记忆——quiz.md 里全是和考试相关的知识，chat.md 里全是对话相关的知识。每种能力调用记忆时，只需要读自己的 L2 文件，精准且高效。L3 则提供跨能力的全局视角，让 Agent 在任何能力模式下都能感知"用户是谁、在学什么、偏好什么"。

### Q3：L1 事件追踪层为什么设计成 append-only？

**答：** 三个原因。

第一，不可变性保证了溯源可靠性。L1 是最底层的原始数据，如果允许修改，引用链（L3 → L2 → L1）的可追溯性就会被破坏。

第二，append 操作极其简单高效。不需要加文件锁，只需要 per-surface 的行级写入锁。操作系统保证文件 append 的原子性，即使进程崩溃，已 append 的行也不会丢失。

第三，避免了"整理时丢失信息"的风险。很多系统在做摘要整合时会丢弃原始数据，但我们保留了完整的历史。L2/L3 可以随时从 L1 重新生成，但 L1 一旦丢失就不可恢复。

### Q4：增量整合是怎么做到不重复处理的？

**答：** 通过 meta 文件追踪已处理的实体引用。

L2 整合时，meta 文件记录了每个已处理的 L1 事件 ID（格式 `surface:event_id`）。每次运行整合时，先读取 meta，对比当前所有 L1 事件，只处理新增的事件。处理完成后更新 meta。

L3 整合同理，但追踪的是 L2 的条目 ID（按 surface 分组）。

这样即使反复触发整合，已处理的数据不会被重复处理。backlog 计数（L2 文件最后修改时间之后的 L1 事件数量）也依赖这个机制——只有未被 L2 处理的事件才计入 backlog。

### Q5：LLM 驱动的整合具体是怎么工作的？

**答：** 整合管道分几个步骤。

首先，从 L1（或 L2）读取新增的实体，渲染为文本。如果文本量较大，按带有 overlap 的滑动窗口切分为多个 chunk。

然后，对每个 chunk 调用 LLM，Prompt 要求从文本中提取事实性知识，每个事实必须带引用（ref）。LLM 返回结构化的事实列表。

接着，验证每个事实的引用是否合法（引用的事件是否确实存在于当前 chunk 的范围内），拒绝无效引用的事实。通过验证的事实追加到 L2（或 L3）文档中。

最后，更新 meta 文件记录已处理的实体。如果配置了自动去重和合并，还会触发后处理。

整个过程是增量的——只处理新增数据，不重新生成整个文档。

### Q6：引用链（Footnote Chain）是怎么设计的？

**答：** 三层引用链：L3 → L2 → L1。

L2 的每个条目带有 `refs` 字段，引用原始 L1 事件的 trace ID。L3 的每个条目引用 L2 的 surface 名称（文件级别），不引用 L2 的条目 ID。

为什么 L3 不直接引用 L1？因为 L1 是按日期分文件的原始日志，entry 数量可能非常大。引用 surface 名称更简洁，给用户一个清晰的导航链：点击 L3 的脚注 → 跳转到对应的 L2 文件 → 再定位到具体的 L1 事件。

Workbench UI 支持这个完整的溯源导航——用户可以点击任意一条记忆，追溯到产生它的原始对话。

### Q7：预览/应用两步流是怎么实现的？

**答：** 预览模式复用了正式的整合管道。

当 `apply_ops=False` 时，系统仍然运行完整的整合流程（调用 LLM、提取事实、写入文档），但记录所有新增条目的 ID，然后**立即删除**这些新增条目。用户通过 SSE 事件流观察到完整的整合过程和结果，但磁盘上不保留变更。

这个设计的好处是预览结果和实际应用完全一致——不存在"预览看到的和实际写入的不同"的问题。代价是预览时仍会短暂写入再删除，不是零写入，但保证了一致性。

### Q8：7 个功能面（Surface）是怎么划分的？为什么不合并？

**答：** 7 个功能面对应 Agent 的 7 种能力模式。

每种能力产生的数据特征不同：chat 产生对话记录，quiz 产生答题数据，notebook 产生笔记，kb 产生知识库操作记录。如果合并成一个大文件，摘要会变得臃肿且不精准。

按功能面隔离的好处：第一，每种能力只读自己的 L2 文件，token 成本可控；第二，摘要可以针对该能力的特点做优化（比如 quiz 的摘要侧重薄弱点，chat 的摘要侧重对话主题）；第三，新增能力只需加一个 surface，不改已有逻辑。

### Q9：如果 LLM 整合失败了怎么办？

**答：** 多层容错。

L1 层：append 失败只记日志不抛异常，不影响主流程。即使 L1 写入完全失败，用户对话仍然正常进行，只是没有记忆。

L2/L3 整合层：每个 chunk 独立处理，单个 chunk 失败不影响其他 chunk。每次 chunk 处理后做 checkpoint 写入，确保中间结果持久化。如果进程崩溃，下次整合从上次 checkpoint 继续，不会丢失已处理的数据。

meta 文件保证了幂等性——即使整合中断，下次运行时 meta 记录的 `seen` 状态会正确跳过已处理的实体。

### Q10：这个记忆系统的扩展性怎么样？

**答：** 三个维度的扩展性。

第一，新增功能面：只需在 `Surface` 类型中加一个值，系统自动为其创建 trace 目录和 L2 文件。不需要改任何已有代码。

第三，L3 槽位扩展：如果需要新的全局维度（比如"社交关系"），只需在 `L3Slot` 中加一个值。

第三，多用户隔离：路径解析通过 `PathService` 延迟获取，每个用户有独立的 `memory_root`。切换用户时，整个记忆目录切换，互不干扰。
